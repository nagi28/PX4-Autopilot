## 10.1 「PX4 との境界線をどこに引くか」という問題

3 つのルートの本質的な違いは、**PX4 と自分のコードの境界をどこに置くか**です。

```
              PX4 が担当                          自分が担当
 ┌──────────────────────────────────────────┬──────────────────┐
 │                                          │                  │
 │ ルート A (Offboard)                       │                  │
 │  推定・全制御・配分・安全機構               │  設定値の生成      │
 │  ← 境界は「trajectory_setpoint」           │  （モードの外側）  │
 ├──────────────────────────────────────────┼──────────────────┤
 │ ルート C (外部モード)                      │                  │
 │  推定・全制御・配分・安全機構               │  設定値の生成      │
 │  ← 境界は同じだが「モードとして統合される」   │  （モードの内側）  │
 ├──────────────────────────────────────────┼──────────────────┤
 │ ルート B (内部実装)                        │                  │
 │  境界を任意の位置に置ける                   │  制御則そのもの     │
 │  （位置制御を丸ごと置き換えることも可能）     │                  │
 └──────────────────────────────────────────┴──────────────────┘
```

- **A と C は「どこへ行くか」を決める**（PX4 が「どう飛ぶか」を担当）
- **B は「どう飛ぶか」まで決められる**

## 10.2 比較表

### 技術特性

| 項目 | A: Offboard | B: PX4 内部 | C: 外部モード |
| --- | --- | --- | --- |
| 実行場所 | コンパニオン | **FMU（フライトコントローラ）** | コンパニオン |
| 実装言語 | 任意（C++/Python/…） | **C++ のみ** | C++ / Python（一部） |
| 制御周期の上限 | 〜100 Hz 程度（実用） | **〜1 kHz** | 〜100 Hz 程度 |
| レイテンシ | 数 ms〜数十 ms | **〜0** | 数 ms〜数十 ms |
| ジッタ | 通信・OS 依存で大きい | **小さい** | 通信・OS 依存で大きい |
| 通信断の影響 | **制御不能→フェイルセーフ** | なし | **制御不能→フェイルセーフ** |
| 利用可能な計算資源 | コンパニオン次第（大） | **FMU の空き（数十 KB RAM）** | コンパニオン次第（大） |
| 外部ライブラリ | 自由（OpenCV, PyTorch, …） | **ほぼ不可** | 自由 |
| 最下層の制御 | 可能だが非推奨 | **可能** | 可能だが非推奨 |

### 開発・運用特性

| 項目 | A: Offboard | B: PX4 内部 | C: 外部モード |
| --- | --- | --- | --- |
| 学習コスト | **低** | 高 | 中 |
| ビルド時間 | **不要**（PX4 再ビルドなし） | 数分〜数十分 | **不要** |
| デバッグ | **容易**（gdb, printf, ROS ツール） | やや難（実機は特に） | **容易** |
| PX4 更新への追従 | **容易**（本体を触らない） | 難（マージ作業） | **容易** |
| 実機に必要なもの | コンパニオン + 通信 | **FMU のみ** | コンパニオン + 通信 |
| 同時に持てる自律機能 | 実質 1 つ | 無制限 | **8 つ** |
| GCS での見え方 | "Offboard" のみ | モードとして正しく見える | **モード名が出る** |
| API 安定性 | **安定** | 内部 API なので変わりうる | 実験的 |

### 安全性

| 項目 | A: Offboard | B: PX4 内部 | C: 外部モード |
| --- | --- | --- | --- |
| アーミングチェックへの参加 | **不可** | 可能 | **可能** |
| 自分の異常を GCS に報告 | 不可 | 可能 | **可能（理由付き）** |
| 必要な推定値の宣言 | 設定値から自動判定 | コンパイル時に決まる | **明示的に宣言** |
| 応答停止の検知 | 設定値タイムアウトのみ | — | **アーミングチェックでも検知** |
| PX4 フェイルセーフとの統合 | 部分的 | **完全** | **ほぼ完全** |
| 内部モードの置き換え | 不可 | 可能（改造） | **可能（フォールバック付き）** |
| フェイルセーフの一時保留 | 不可 | 可能 | **`ConfigOverrides`** |

## 10.3 失敗時の挙動比較

**自律制御を実機で動かすなら、ここが最も重要です。**

| 障害 | A: Offboard | B: PX4 内部 | C: 外部モード |
| --- | --- | --- | --- |
| 自分のプログラムがクラッシュ | `COM_OF_LOSS_T` 経過後にフェイルセーフ（`COM_OBL_RC_ACT`） | モジュールが止まる → 制御段が設定値を受け取れずフェイルセーフ | 設定値タイムアウト **+ アーミングチェック無応答**の両方で検知 |
| コンパニオンごと停止 | 同上 | 影響なし | 同上 |
| 通信リンク断（有線が抜けた等） | 同上 | 影響なし | 同上 |
| 自分のロジックが異常値を出す | **PX4 は気づけない**（設定値の範囲制限のみ） | 同左 | 同左 |
| 前提条件が崩れた（マップ喪失等） | **PX4 に伝えられない** | チェックを実装できる | **`ArmingCheckReply` で伝えられる** |
| FMU 自体の異常 | PX4 のフェイルセーフ | PX4 のフェイルセーフ | PX4 のフェイルセーフ |

> [!WARNING]
> **どのルートでも「自分のロジックが異常値を出す」ケースは PX4 が守ってくれません。**
> PX4 は設定値の範囲（速度上限・傾斜角上限など）は守りますが、
> 「間違った方向へ全速力で飛ぶ」ことは止められません。
>
> **必ずジオフェンス（`GF_ACTION`, `GF_MAX_HOR_DIST`, `GF_MAX_VER_DIST`）を設定し、
> RC 送信機で手動に戻せる状態を保ってください。**

## 10.4 選定フローチャート

```
                    ┌──────────────────────────┐
                    │ 何を作りたいか？            │
                    └────────────┬─────────────┘
                                 │
         ┌───────────────────────┼───────────────────────┐
         │                       │                       │
   独自の制御則を          「どこへ行くか」を         PX4 の既存モードを
   試したい                 決めたい                改良したい
   （姿勢・角速度制御）                                （RTL, Orbit 等）
         │                       │                       │
         ▼                       │                       ▼
  ┌─────────────┐                │              ┌─────────────────┐
  │ ルート B     │                │              │ ルート C         │
  │ PX4 内部実装 │                │              │ 外部モード       │
  └─────────────┘                │              │ （モード置き換え）│
                                 │              └─────────────────┘
              ┌──────────────────┼──────────────────┐
              │                  │                  │
        重い計算が必要？      まず動かしたい      本番運用したい
        （SLAM/認識/学習）    （実験・研究）      （複数モード/安全）
              │                  │                  │
              ▼                  ▼                  ▼
      コンパニオン必須     ┌─────────────┐   ┌─────────────┐
              │           │ ルート A     │   │ ルート C     │
              ▼           │ Offboard     │   │ 外部モード   │
      ┌─────────────┐     └─────────────┘   └─────────────┘
      │ A または C   │
      │ （本番なら C）│
      └─────────────┘
```

### 目的別の推奨

| やりたいこと | 推奨ルート | 理由 |
| --- | --- | --- |
| まず自律飛行を体験したい | **A: Offboard** | 最短で動く。PX4 を触らない |
| 大学の研究で軌道最適化を試す | **A: Offboard** | 実装が速く、Python も使える |
| SLAM ベースの屋内自律飛行 | **A → C** | まず A で試し、本番は C へ移行 |
| 独自の姿勢制御則（適応制御など） | **B: PX4 内部** | レイテンシとレートが要件 |
| 強化学習ポリシーを機体で動かす | **B**（`mc_raptor` 参照） | 高レート推論が必要 |
| 配送ドローンの製品開発 | **C: 外部モード** | 複数モード + 安全統合が必須 |
| 検査ドローン（複数の飛行パターン） | **C: 外部モード** | 8 枠を使い分けられる |
| RTL をもっと賢くしたい | **C**（モード置き換え） | フォールバックがある |
| ミッションの新しいコマンド | **B**（navigator 拡張） | ミッション実行は PX4 内部 |
| センサドライバの追加 | **B**（`src/drivers/`） | ハードウェア直結 |

## 10.5 段階的な進め方（推奨）

**いきなり最終形を目指さないでください。** 現実的な進め方はこうです。

```
第 1 段階: SITL + Offboard で概念実証
  ├─ make px4_sitl gz_x500
  ├─ ROS 2 ノードから trajectory_setpoint を送る
  └─ 「自分のアルゴリズムで飛ぶ」ことを確認
        │
        ▼
第 2 段階: SITL で安全性を詰める
  ├─ 通信断、推定劣化、フェイルセーフの挙動を確認
  ├─ ジオフェンスとフェイルセーフパラメータを設定
  └─ ログ（ULog）で挙動を検証
        │
        ▼
第 3 段階: 外部モードへ移行（本番を目指す場合）
  ├─ px4_ros2 ライブラリで書き直す
  ├─ アーミングチェックに自分の条件を登録
  └─ GCS にモードが出ることを確認
        │
        ▼
第 4 段階: 実機（屋内・テザー・低高度から）
  ├─ RC 送信機で手動に戻せる状態を必ず確保
  ├─ ジオフェンスを狭く設定
  └─ 少しずつ条件を広げる
        │
        ▼
（必要なら）第 5 段階: 制御則を PX4 内部へ
  └─ レイテンシやレートが足りない部分だけを内部実装に移す
```

> [!TIP]
> **A で書いたコードは C へほぼそのまま移行できます。**
> どちらも「設定値を生成して送る」ロジックは同じで、
> 違いは登録・アーミングチェック・ライフサイクルの部分だけです。
> **だから最初は A で始めるのが合理的です。**

## 10.6 組み合わせて使う

3 つは排他ではありません。実際の製品では組み合わせるのが普通です。

```
┌─────────────────────────────────────────────────────────┐
│ コンパニオンコンピュータ                                    │
│                                                          │
│  ・SLAM / 物体認識            → vehicle_visual_odometry   │
│  ・経路計画                   → 外部モード（ルート C）      │
│  ・障害物検出                 → obstacle_distance         │
└─────────────────────────────────────────────────────────┘
                            ↕ uXRCE-DDS
┌─────────────────────────────────────────────────────────┐
│ FMU (PX4)                                                │
│                                                          │
│  ・EKF2（外部 Vision を融合）                              │
│  ・独自の姿勢制御則           ← ルート B                    │
│  ・標準の位置制御・推力配分                                 │
│  ・commander / フェイルセーフ                              │
└─────────────────────────────────────────────────────────┘
```

**役割分担の原則:**

| FMU（PX4 内部） | コンパニオン |
| --- | --- |
| 高レート・低レイテンシ | 重い計算 |
| 安全に直結する処理 | 外部ライブラリが必要な処理 |
| 通信断でも動かねばならない処理 | 頻繁に更新したい処理 |
| 姿勢・角速度制御、推力配分 | 認識、SLAM、経路計画、意思決定 |

## 10.7 判断に迷ったときのチェックリスト

以下に **1 つでも「はい」があれば ルート B（PX4 内部）** を検討してください:

- [ ] 制御周期が 100 Hz を超える必要がある
- [ ] 姿勢制御・角速度制御そのものを変更したい
- [ ] コンパニオンコンピュータを機体に載せられない
- [ ] 通信が切れても制御を続けなければならない

以下に **1 つでも「はい」があれば ルート C（外部モード）** を検討してください:

- [ ] 自律機能を複数持ちたい（探索モード、配送モード、…）
- [ ] 運用者に「今どのモードか」を分かるようにしたい
- [ ] 自分のプログラムの前提条件をアーミングチェックに反映したい
- [ ] PX4 の既存モード（RTL など）を自作版に置き換えたい
- [ ] 製品として運用する（研究・実験ではない）

**どちらにも該当しなければ、ルート A（Offboard）で始めてください。**
最も早く動き、後から C へ移行できます。

## 10.8 この章のまとめ

- 3 ルートの本質的な違いは **PX4 と自分のコードの境界線をどこに引くか**
- **A（Offboard）**: 最も手軽。実験・研究・プロトタイプ向け
- **B（PX4 内部）**: 唯一「どう飛ぶか」を変えられる。高レート制御が必要なら必須
- **C（外部モード）**: 本番運用向け。安全機構と完全に統合される
- **A で始めて C へ移行、必要な部分だけ B**、という進め方が現実的
- 実際の製品では 3 つを **組み合わせる**
- **どのルートでも、ジオフェンスと手動復帰手段は必ず用意すること**
